# deploy

Ensures the CI is configured, reviews the code, then commits and pushes to trigger the
GitHub Actions deployment pipeline.

---

## Step 1 — Check if the CI workflow exists

Run:

```bash
ls .github/workflows/deploy.yml 2>/dev/null
```

- **File absent** → the project has no CI configured. Tell the user:

  > No CI workflow found. Running ea-deploy-setup first.

  Invoke the `ea-deploy-setup` skill. Wait for it to complete, then continue to Step 2.

- **File found** → continue to Step 2.

---

## Step 2 — Audit the CI for heavy checks

Before deploying, make sure the CI workflow only does what a CI has to do
(deploy + run migrations on the server). Anything that is a **code-quality
check** — lint, formatting, static analysis, unit tests — should run locally
in a pre-commit hook, not in the deploy pipeline. Heavy checks in the deploy
pipeline slow every deploy down and, worse, only catch problems **after** the
code is already pushed to `main`.

### 2.1 — List and read every workflow file

List every workflow file in `.github/workflows/`:

```bash
ls .github/workflows/*.yml .github/workflows/*.yaml 2>/dev/null
```

Read **every** file returned — not just `deploy.yml`. Projects often keep
their lint / test pipelines in separate files (`ci.yml`, `test.yml`,
`lint.yml`, `quality.yml`, …), so the audit must cover all of them.

Store the file list as `workflowFiles`.

### 2.2 — Detect heavy checks

For each file in `workflowFiles`, walk every job and every `run:` step.
Flag a step as a **heavy check** if its shell command (or one of the
commands, when chained with `&&` or `;`) matches any of the patterns below:

| Ecosystem | Command patterns |
|---|---|
| JS / TS | `npm test`, `npm run test*`, `npm run lint*`, `npm run typecheck`, `yarn test`, `yarn lint`, `pnpm test`, `pnpm lint`, `jest`, `vitest`, `eslint`, `prettier`, `tsc --noEmit`, `biome`, `standardjs` |
| PHP | `phpunit`, `vendor/bin/phpunit`, `phpstan`, `vendor/bin/phpstan`, `phpcs`, `vendor/bin/phpcs`, `psalm`, `pint`, `rector`, `phpmd` |
| Python | `pytest`, `python -m unittest`, `ruff`, `black`, `flake8`, `mypy`, `pylint`, `isort` |
| Ruby | `rspec`, `bundle exec rspec`, `rubocop`, `bundle exec rubocop`, `minitest`, `rake test` |
| Go | `go test`, `golangci-lint`, `staticcheck` |
| Rust | `cargo test`, `cargo clippy`, `cargo fmt --check` |
| Generic | `make lint`, `make test`, `make check`, `pre-commit run` |

Deploy-related commands are **not** heavy checks and must be left in place —
never flag: `ssh-action`, `git clone`, `git pull`, `docker compose ...`,
`docker build`, `rsync`, migration commands, or anything already inside the
`deploy` or `migrate` jobs' SSH `script:` block.

For every match, record: `filePath`, `jobName`, `stepName` (or index), and
the exact command line.

Build the list `heavyChecks`.

### 2.3 — If nothing was flagged

If `heavyChecks` is empty, display:

```
✓ CI audit clean — no heavy checks found in any workflow under .github/workflows/
```

Go to **Step 3**.

### 2.4 — Present the findings

Display the flagged items in a plain, non-technical list, grouped by file:

```
Your GitHub Actions currently run the following checks. These slow every
run down and only fail *after* the code is on main — they belong in a
pre-commit hook so they run on your machine before a commit is ever created:

  <filePath>
    • <jobName> / <stepName> — <command>
    • <jobName> / <stepName> — <command>
  <filePath>
    • <jobName> / <stepName> — <command>
  ...
```

Then ask:

```
AskUserQuestion:
  question: "Move these checks from GitHub Actions to a pre-commit hook?"
  header: "CI audit"
  options:
    - label: "Move to pre-commit (Recommended)"
      description: "Remove them from the workflow files and install a local pre-commit hook that runs them before each commit"
    - label: "Keep them in the CI"
      description: "Leave the workflows as-is and continue with the deploy"
    - label: "Cancel deploy"
      description: "Stop here — no changes made, no deploy triggered"
```

- **Cancel deploy** → stop.
- **Keep them in the CI** → go to **Step 3**.
- **Move to pre-commit** → continue to **2.5**.

### 2.5 — Install the pre-commit hook

**2.5.1 — Build the hook script**

Check whether a `pre-commit` file already exists at the project root.

- **If it does not exist** → create it with the following content:

  ```sh
  #!/usr/bin/env sh
  # Auto-generated by ea-deploy — runs the checks that used to live in
  # .github/workflows/*.yml. Edit freely; keep the shebang line.
  set -e

  <one line per flagged command, in the original order>
  ```

- **If it already exists** → read it, then append each flagged command that
  is not already present as an exact-match line. Do **not** rewrite or
  reorder existing lines. If every flagged command is already there, skip
  the write.

Make sure the file is executable:

```bash
chmod +x pre-commit
```

**2.5.2 — Wire it into git**

Install (or replace) the git hook that runs it:

```bash
mkdir -p .git/hooks
cat > .git/hooks/pre-commit <<'HOOK'
#!/usr/bin/env sh
# Installed by ea-deploy — delegates to the tracked ./pre-commit script.
exec "$(git rev-parse --show-toplevel)/pre-commit"
HOOK
chmod +x .git/hooks/pre-commit
```

The `.git/hooks/pre-commit` is a thin shim — the real logic lives in the
tracked `pre-commit` file so a new teammate only needs to re-run the shim
install (or `ea-deploy` again) after cloning.

**2.5.3 — Update the workflow files**

For each `filePath` that had at least one flagged item, edit it and remove
the flagged pieces:

- If a **whole job** contained nothing but heavy-check steps → delete the
  entire job block, and remove that job name from any `needs: [...]` list on
  the remaining jobs (in the same file).
- If a job contained a **mix** of heavy checks and other work → remove only
  the flagged `- name:` step blocks, keep the rest of the job intact.
- If, after removals, a workflow file has **no jobs left**, delete the whole
  file (`rm <filePath>`) — an empty `jobs:` section is invalid YAML and will
  break GitHub Actions.
- Never touch the `deploy` job or the `migrate` job in
  `.github/workflows/deploy.yml` — they must remain exactly as
  `ea-deploy-setup` produced them.

**2.5.4 — Confirm**

Display:

```
✓ Pre-commit hook installed at ./pre-commit
✓ .git/hooks/pre-commit wired up
✓ Removed <n> heavy check(s) across <m> workflow file(s):
    <filePath> — <k> removed[, file deleted (no jobs left)]
    <filePath> — <k> removed
    ...

The checks will now run automatically before every commit on your machine.
They will be committed and pushed with the rest of your changes.
```

Continue to **Step 3**.

---

## Step 3 — Review and push

Invoke the `ea-github-commit` skill.

The `ea-github-commit` skill handles the full sequence:
- Pull latest changes and resolve any conflicts
- Run a code review (`ea-code-review` skill) before committing
- Generate a commit message and ask for confirmation
- Commit and push

Wait for `ea-github-commit` to complete.

---

## Step 4 — Deployment summary

Once `ea-github-commit` has pushed successfully, display:

```
✓ Deploy triggered

Your changes have been pushed to main.
GitHub Actions will now run the deployment pipeline:
```

Then read `.github/workflows/deploy.yml` to check whether a `migrate` job is present.

- **If `migrate` job found:**

  ```
    1. migrate — runs database migrations on the server
    2. deploy  — pulls the code and restarts containers
  ```

- **If no `migrate` job:**

  ```
    1. deploy — pulls the code and restarts containers
  ```

Then append:

```
Track the deployment at:
https://github.com/northstar-network/<projectName>/actions

Production URL: https://<productionHostname>
```

To get `projectName`, run:

```bash
basename "$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
```

To get `productionHostname`, read `TRAEFIK_HOSTNAME` from `.env.prod`:

```bash
grep "^TRAEFIK_HOSTNAME=" .env.prod 2>/dev/null | cut -d= -f2
```

- If the value is found → use it as `productionHostname`.
- If `.env.prod` is absent or the variable is not set → use `<projectName>.easydeploy.tech` as the fallback.

## Rules

- If invoked by the `easydeploy` skill, resume the `easydeploy` skill when this skill finishes — do not stop.
- **Never** push without first ensuring the CI workflow exists — always check in Step 1.
- **Never** invoke `ea-github-commit` if `ea-deploy-setup` failed or was cancelled — stop instead.
- **Never** touch the `deploy` or `migrate` jobs in the CI audit (Step 2) — only remove flagged lint/test items.
- **Never** delete an existing tracked `pre-commit` file — if it already exists, append the new commands (dedup identical lines) instead of overwriting.
- The code review is handled inside `ea-github-commit` — do not invoke `ea-code-review` separately.
- **Language — English only:** All output from this skill must be in English. This applies to all messages shown to the user, error messages, and any other text produced. If the user writes in another language, understand them but always reply and generate output in English.
